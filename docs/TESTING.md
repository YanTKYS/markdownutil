## v0.1.0

実施日: 2026-08-13
方法: `python3 -m http.server` で `markdownutil/` を静的配信し、実ブラウザ（Chromium /
Playwright経由）から操作して確認。文書サンプルはWord/Excel/PowerPoint/PDFはPython

自治体等の実業務で使われる文書にありがちな、結合セルを多用した帳票Word、複雑な図形を

「基本的な変換性能を確認できた」という段階までであり、実業務文書での変換品質はIIS実機配置後、
庁内の実文書を用いて別途確認する。

### 既知の制限（v0.2.0で追加）

- スライドプレビューは、AnyDocが生成した通常のMarkdownを自動でスライドへ整形するものではない。
  見出しごとの自動`---`挿入や枚数の自動決定は行わないため、意図した区切りでスライド化するには
  利用者がMarkdown側に`---`やfront matterを追記する必要がある。
- 元のMarkdown中に水平線としての`---`単体行が含まれる場合、Marpの仕様上スライド区切りとして
  解釈される。AnyDocが変換した文書に水平線が含まれるケースは今回のテストでは確認していない。
- スライド用のテスト対象はMarp記法として典型的な内容（見出し・箇条書き・表・コードブロック・
  テーマ切替）にとどまり、数式（MathJax）・画像埋め込み・スピーカーノート等、Marpのより
  高度な機能は今回個別に検証していない。

## v0.2.1（スライドモード表示制御の回帰修正）

実施日: 2026-08-13
方法: v0.2.0と同じくPlaywright経由のChromiumで確認。新機能は追加せず、CSSの1箇所を修正した。

### 修正した問題

`css/app.css`の`.slide-toolbar`が`display: flex`を無条件に指定していたため、
`index.html`側の`hidden`属性（HTMLの`hidden`属性はUAスタイルシートの
`[hidden] { display: none }`によって非表示になる）が、詳細度に関係なく作者スタイルシートの
`display`指定によって上書きされ、文書モードでもスライド専用ツールバー（テーマ・HTML出力・
印刷・プレゼン表示）が実際には表示されてしまう状態だった。v0.2.0時点のテストは`hidden`
「属性」の有無（`getAttribute('hidden')`）のみを確認しており、実際の描画結果
（`getComputedStyle().display`）までは確認していなかったため、この問題を検出できていなかった。

`.slide-toolbar`から`display: flex`を外し、`.slide-toolbar:not([hidden]) { display: flex; }`
へ変更することで、`hidden`属性がある限り確実に非表示になるようにした。同様のパターンが
他の要素（`#preview` / `#slide-frame` / `#presenter-hint`）にも無いか確認したが、これらは
`display`を明示的に指定していないため、`hidden`属性は元から正しく機能していた。

### 追加確認したテスト

| # | 内容 | 結果 |
| --- | --- | --- |
| 1 | 文書モード時、`#slide-toolbar`の`hidden`属性が付与されている | OK |
| 2 | 文書モード時、`#slide-toolbar`の`getComputedStyle().display`が`none`である（修正前は`flex`のまま表示されていた） | OK（修正後） |
| 3 | 文書モード時、テーマ選択欄・HTML出力・印刷・プレゼン表示ボタンが`isVisible()`で不可視 | OK |
| 4 | スライドモードへ切替後、`#slide-toolbar`の`getComputedStyle().display`が`flex`になり、各操作ボタンが`isVisible()`で可視になる | OK |
| 5 | スライドモードから文書モードへ戻すと、再び`display: none`・不可視に戻る | OK |
| 6 | `#preview` / `#slide-frame`のモード切替時の`getComputedStyle().display`（`none`⇔表示）も合わせて確認 | OK（元から問題なし） |
| 7 | v0.2.0で実施した全テスト（AnyDoc変換・通常プレビュー・コピー・保存・D&D・スライド表示・テーマ・HTML出力・印刷・プレゼン表示・キーボード操作・クリア） | OK（回帰なし） |
| 8 | 外部通信・consoleエラー | 0件（回帰なし） |

### v0.2.1まとめ

スライド専用ツールバーが文書モードでも実際には表示されてしまう回帰を修正した。原因は
CSSの`display`指定がHTMLの`hidden`属性を上書きしていたことで、`:not([hidden])`で
スコープすることで解決した。今後同様の問題を早期に検出できるよう、モード切替の確認は
DOM属性だけでなく`getComputedStyle().display`と`isVisible()`の両方で行うようにした。

一切反応しない時間が生じていた。文書変換しか使わない職員も必ずこの待ち時間を負担していた。

**修正**: スライドモードが初めて使われたときに動的import（`import()`）で読み込むようにした。

## v0.2.3（スライド出力の状態整合性修正）

実施日: 2026-08-13
方法: Playwright経由のChromiumで確認。Marpの`render()`を差し替え、成功/失敗を明示的に
切り替えられるようにした上で検証した。

### 修正した問題

Marpの解析に失敗した場合、`slide-preview.js`は直前の正常なプレビュー（`lastRendered`/
`slideCount`）を画面に残す設計だった。これ自体は意図どおりだが、`app.js`側の`hasSlides()`は
「`slideCount > 0`か」だけを見て出力系操作（HTML出力・印刷・プレゼン表示）を許可していたため、
以下の手順で**「今のMarkdownではなく、直す前の内容」が出力できてしまっていた**。

```text

        ↓
Markdownを壊す → 画面には解析エラー表示、スライド自体は直前の内容のまま
        ↓
「HTML出力」を押す → 壊す前の内容が保存されてしまう（バグ）
```

実際に強制的に解析を失敗させて再現したところ、HTML出力・印刷・プレゼン表示のいずれも
「壊す前の正常な内容」で実行できてしまうことを確認した。

### 修正

`slide-preview.js`に、直前の表示が現在のMarkdownを正しくレンダリングした結果かどうかを
示す`renderValid`を追加した。`render()`が成功した場合のみ`true`、解析に失敗した場合は
`false`にする（表示自体は直前の内容を残す従来の挙動は変えていない）。`isRenderValid()`を
新たにexportし、`app.js`の`hasSlides()`で`slideCount > 0`に加えて確認するようにした。
解析エラー中に出力系ボタンを押した場合は「Markdownにエラーがあるため実行できません。
スライドの表示内容を確認してください。」と表示し、実行を止める。

## v0.2.4（スライド描画内容とMarkdown編集状態の整合性修正）

実施日: 2026-08-13
方法: Playwright経由のChromiumで確認。Marpの`render()`を差し替え、入力内容をそのまま
スライドの見出しへ反映するようにして、どの版の内容が出力されたかを判別できるようにした。

### 修正した問題

v0.2.3で追加した`renderValid`は「直前の`render()`が成功したか」だけを表しており、
「その成功結果が今のエディタの内容と一致しているか」までは保証していなかった。そのため
以下の状況で、出力系操作（HTML出力・印刷・プレゼン表示）が**編集中の最新内容ではなく、
直前に描画が完了していた古い内容**を出力できてしまっていた。

- Markdownを編集した直後、プレビュー更新のdebounce（150ms）が完了する前に操作した場合
- モードを切り替えた直後、Marpの再描画（非同期）が完了する前に操作した場合

実際に、debounce待機中（入力から50ms後）にHTML出力を押すと、編集前の内容
（「スライドA」）がダウンロードされてしまうことを確認した。

### 修正

`slide-preview.js`の`renderValid`（真偽値）を`renderedSource`（最後に正しく
レンダリングできたMarkdownそのもの）に置き換えた。`render()`成功時に
`renderedSource = markdown`として入力を記録し、解析失敗時や読み込み失敗時は`null`に
戻す。新たに`isRenderCurrent(markdown)`をexportし、「渡されたMarkdownが、最後に
成功した描画の入力と一致するか」を判定できるようにした。`app.js`の`hasSlides()`は
`isRenderCurrent(editor.value)`で確認するように変更した。

真偽値だけを追跡する方式（編集イベントのたびに`renderValid = false`にする等）ではなく、
入力そのものを記録して比較する方式にしたことで、ファイル読込・テーマ変更・クリアなど
Markdownを書き換える経路が今後増えても、比較対象を追加登録し忘れて判定漏れが起きる
心配がない。

## v0.3.1（プレゼン全画面操作の回帰修正）

実施日: 2026-08-13
方法: Playwright経由のChromiumで確認。新機能は追加せず、`js/presenter.js`のバグを1件修正した。

### 修正した問題

プレゼン専用ウィンドウ右下の「⛶ 全画面」ボタンに`stopPropagation()`が無かったため、
クリックがドキュメント全体のクリックリスナー（クリックで次のスライドへ進む処理）へ伝播し、
**全画面化と同時にスライドが1枚進んでしまっていた**。実際に3枚のMarkdownでプレゼンを開始し
（1/3）、全画面ボタンを押すと位置表示が2/3になることを確認した。「外部ディスプレイへ移動 →
全画面ボタン → 発表開始」という想定利用フローの入口で必ず発生する不具合だった。

`mu-fullscreen-btn`のクリックハンドラの先頭で`event.stopPropagation()`を呼ぶよう修正し、
全画面化してもスライドの位置が変わらないことを確認した。あわせて、`:fullscreen
.mu-fullscreen-btn { display: none; }`を追加し、全画面化した後は投影内容がスライドだけに
なるようにした（Escキーで全画面を解除できるため、ボタンを常に表示しておく必要は薄いと判断）。

同種の問題（ボタンのクリックがスライド送りへ伝播する）が他に無いかを確認したところ、
HTML出力のスライドショー（`slide-preview.js`の`buildStandaloneHtml()`）側は元から
`ss-next` / `ss-prev` / `ss-notes-toggle` / `ss-fullscreen`すべてに`stopPropagation()`が
入っており、影響は無かった。

| --- | --- | --- |
| 1 | 1/3でプレゼン開始 | OK |
| 2 | 全画面ボタンをクリック | OK |
| 3 | クリック後も位置が1/3のまま（修正前は2/3になっていた） | OK |
| 4 | 全画面時に`.mu-fullscreen-btn`を隠すCSSルールが存在する | OK |
| 5 | 発表者ビューの「次へ」ボタンによる通常の移動は引き続き機能する | OK |
| 6 | プレゼン専用ウィンドウのスライド本体をクリックした場合の「次へ」進む挙動は維持される（全画面ボタン以外のクリックまで止めていないことの確認） | OK |

v0.2.4までの状態整合性チェック、v0.3.0のプレゼン専用ウィンドウ・発表者ビュー・同期・
HTML出力・印刷の各テストを再実行し、回帰がないことを確認した。外部通信0件、
consoleエラー0件。

### v0.3.1まとめ

プレゼン専用ウィンドウの「全画面」ボタンが、意図せずスライドを1枚進めてしまう不具合を
修正した。原因はクリックイベントの伝播を止めていなかったことで、`stopPropagation()`の
追加で解決した。あわせて全画面時にボタン自体を隠し、投影内容をスライドだけにした。
変更は`js/presenter.js`の1箇所（クリックハンドラとCSS）のみ。

## v0.4.0（編集支援ヘルプ: Markdown / Marp 早見表）

実施日: 2026-08-13
方法: Playwright経由のChromiumで確認。既存の回帰テストスクリプト（v0.1.0〜v0.3.1分）も
すべて再実行した。

### 実装方針の要点

- `js/help.js`（新規）を追加し、早見表データ（名称・簡単な説明・記法例の配列）、
  モーダルの開閉・タブ切替・記法例のクリップボードコピーをここへ集約した。`app.js`は
  DOM要素の受け渡しとボタンの配線のみ（早見表データやUI生成コードは持ち込んでいない）。
  `converter.js` / `preview.js` / `slide-preview.js` / `presenter.js`は変更していない。
- 記法例はすべて`textContent`でDOMへ設定しており、`innerHTML`は使用していない。
  Markdown/MarpのコードフェンスやHTMLコメントを含む記法例（例:
  `` ```text ... ``` ``、`<!-- _class: lead -->`）がそのままエスケープされずに文字列として
  表示され、実行やレンダリングの対象にならないことを確認した。
- コピー機能は`app.js`のコピー処理と同じ実装パターン（Clipboard API、失敗時は
  `execCommand('copy')`にフォールバック）を`help.js`内に持ち、コピー結果は`app.js`から
  渡された`onStatus`コールバック経由で既存のステータス表示へ出す（独自の通知UIは追加していない）。
- モーダルの開閉は`hidden`属性で行い、v0.2.1の教訓（`display`を無条件指定すると`hidden`属性が
  上書きされる）を踏まえて`.help-overlay:not([hidden]) { display: flex; }`とした。

### v0.4.0まとめ

Markdown編集領域に「? ヘルプ」ボタンと、Markdown / Marpの記法早見表（タブ切替・記法例の
コピー）を追加した。早見表は`js/help.js`へ分離し、`app.js`の肥大化を避けた。記法例は
すべて`textContent`で扱っているためMarkdownとして解釈されたり崩れたりすることはなく、
コピー操作もエディタの内容に影響しない。閉じるボタン・`Esc`・背景クリックのいずれでも
閉じられ、閉じた後はヘルプボタンへフォーカスが戻る。既存のAnyDoc変換・スライド機能・
プレゼン機能・状態整合性制御に回帰がないことを確認した。

### 既知の制限（v0.4.0で追加）

- 早見表はMarkdown/Marpの代表的な記法の一覧であり、仕様を網羅した解説ではない。
- コピーした記法例をエディタのカーソル位置へ自動挿入する機能はない（貼り付けは手動）。
- 早見表の内容はMarkdownUtil側に固定されており、利用者が項目を追加・編集する機能はない。
- 初回起動時にヘルプを強制表示する機能はない（利用者が「? ヘルプ」を押した場合のみ表示）。

## v0.4.1（ヘルプのキーボード操作・コピー後フォーカス改善）

実施日: 2026-08-13
方法: Playwright経由のChromiumで確認。新機能は追加せず、`js/help.js`のキーボード・
フォーカス関連の不具合を修正した。

### 修正した問題

**1. Tab/Shift+Tabでダイアログの外（背面の通常画面）へ抜けられる**

`role="dialog" aria-modal="true"`を名乗っていたが、`keydown`ではEscapeしか処理しておらず、
Tabキーの移動先を制御していなかった。実際に確認したところ、ヘルプを開いた状態で`Tab`を
13回押すとダイアログ外へフォーカスが抜け、`Shift+Tab`は1回目で背面の「スライド」タブ
ボタンへ直接フォーカスが移ってしまうことを確認した。見た目はモーダルなのに、キーボード
操作だけで背面のUIを操作できてしまう状態だった。

**2. `execCommand('copy')`フォールバック後、フォーカスがコピー元ボタンへ戻らない**

Clipboard APIが使えない環境（HTTP配信のIIS等でよくある）では一時`<textarea>`へ`focus()`して
コピーする経路（`legacyCopy()`）を通るが、コピー後にその一時要素を削除するだけでフォーカスを
戻していなかった。実際に確認したところ、コピー後のフォーカスが`<body>`に落ちることを確認した。

### 修正

- ダイアログ内の実際に見えている（隠れているタブパネル内ではない）フォーカス可能要素を
  取得し、`Tab`で末尾から先頭へ、`Shift+Tab`で先頭から末尾へ折り返す`trapTab()`を追加した。
- `copySnippet()`にコピー元のボタン要素を渡すようにし、`finally`節で
  （Clipboard API経路・`legacyCopy()`経路のいずれでも）コピー元のボタンへフォーカスを
  戻すようにした。
- `Esc`で閉じた場合の挙動（「? ヘルプ」ボタンへフォーカスを戻す）は既存のまま変更していない。

あわせて、レビューで軽微なUXとして挙げられた「コピー成功通知がオーバーレイの背面にあり
気づきにくい」点について、コピー元のボタン自体を一時的に「コピー済み」表示へ切り替える
`flashCopied()`を追加した（1.2秒後に元の表示へ戻る）。既存のステータス表示による通知は
そのまま維持しており、独自の大きな通知UIは追加していない。

ヘルプモーダルがキーボード操作でも実際にモーダルとして振る舞うよう、Tab/Shift+Tabを
